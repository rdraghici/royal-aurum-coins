# Engineering conventions

A starting point to edit before task T-001, not a finished standard. The first rule outranks
the rest: **write the plain solution; add a pattern only when this page names it for the
situation at hand.** Each convention that can be checked by a tool is listed in
[quality-gates.md](quality-gates.md); those are binding, the rest is guidance for review.

## Shape of the system

One Spring Boot application (`apps/api`), one Next.js application (`apps/web`), one PostgreSQL
database. No microservices, no message broker, no cache until a measurement asks for one.

## API layout

Base package `com.royalaurumcoins.api`, organised by type first, then by domain:

```
controller/<domain>   REST endpoints; request and response DTOs only
dto/<domain>          records; Bean Validation on requests
service/<domain>      use cases and rules; transactions start here
model/<domain>        enums, state machines, value types, domain events
entity/<domain>       JPA entities (Lombok @Getter/@Setter/@Builder)
repository/<domain>   Spring Data repositories
integrations/<name>   one package per external provider (payment, email, storage, newsletter)
config/  exception/   cross-cutting, flat
```

Domains follow the product definition's bounded contexts: `catalogue`, `order`, `payment`,
`account`, `intake`, and in Phase 2 `marketplace` and `offer`. Use the product's own words for
names (`Coin`, not `Product`; `Reservation`, `Listing`, `WeBuySubmission`): the glossary is
`docs/product/model/domain/terms/`.

## Patterns this project uses, and when

| Situation | Pattern | Not for |
| --- | --- | --- |
| Talking to an external provider | An interface in `service/<domain>` owned by us, one implementation per provider in `integrations/<name>` | Internal collaborators: no interface with a single implementation |
| Something with a lifecycle (order, reservation, submission, listing, offer) | An explicit status enum and one class holding the allowed transitions; an illegal transition throws; every transition has a unit test | Simple flags |
| A side effect that must follow a database change (email, provider call) | Transactional outbox: write the intent in the same transaction, a worker delivers it, deliveries are idempotent | Reads; in-process calls |
| Calling a provider | Idempotency key per logical operation; timeouts; retry only what is safe to repeat | |
| Receiving a webhook | Verify the signature on the raw body, store the provider's event ID, ignore repeats | |
| A value the Client can configure (reservation period, threshold, commission) | A settings table edited in the administration panel (CON-OPS-001) | Environment variables, constants |
| Anything depending on time | Take a `Clock`; tests fix it | `now()` calls |
| Money | Integer minor units (`long` cents), euro only (CON-LOCALE-001) | `double`, `float` |
| Errors returned by the API | RFC 9457 problem details from one exception handler | Ad-hoc error bodies |
| Identifiers | UUID, generated by the application | Sequential IDs in URLs |

What is deliberately absent: generic base services or repositories, an event bus, CQRS,
mappers generated by a framework, a cache layer. Add one only with a reason written in the pull
request.

## Rules that come from the Agreement

- **Payments go through one interface (CON-PAY-001).** From Phase 1 onwards, because the card
  processor itself may need replacing. The interface speaks in the product's terms: take a
  payment, hold it, release it net of commission, refund it. It must also allow payouts that
  the Client executes manually.
- **Server-side validation and role checks on everything (CON-SEC-001).** The browser's
  validation is a convenience. Card data never reaches our servers.
- **No AGPL or similar licences (CON-TECH-001).** Check the licence before adding a dependency.
- **Synthetic data only outside production (CON-DATA-001).** Seed data is invented. Production
  data is never copied into development, tests, staging, logs or prompts.
- **Nothing on the excluded list gets built (CON-SCOPE-001).** A request that needs it stops and
  becomes a Change Request.

## Database

Flyway, one migration per change, named `V<n>__<what>.sql`. A migration that has reached `main`
is never edited; write the next one. Constraints live in the database as well as in the code:
a coin can be sold once because a unique constraint says so, not because a service checked.

## Web

Server components by default; client components only where there is interaction. All data
comes through `lib/api` and the generated types. Forms validate with the same rules as the
server, but the server's answer is the one that counts. No business rule lives only in the UI.
English only, prices formatted in euro in one place.

## Tests

Test behaviour, not structure. A test that would still pass if the rule were deleted is not a
test. Prefer a real database (Testcontainers) to mocks for anything that touches persistence.
Each structured behaviour of the product definition has a test that names it.
