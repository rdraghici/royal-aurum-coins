# Royal Aurum Coins — project guide

A curated online shop for certified historical gold coins (Phase 1) and a curated marketplace
for private sellers (Phase 2), built for a client under a fixed-scope agreement. This file
loads every session. Read it, then pull the task, the product rules and the docs you need.

## Working agreements (non-negotiable)

1. **Build what the product definition says, and only that.** The rules are in
   `docs/product/model/`. A task cites them; it does not restate them. If a rule you need is
   missing, is a `draft`, is reported stale, or contradicts another: **stop and report**. Do
   not guess, and do not pick the likely answer. Anything on the excluded list
   (CON-SCOPE-001) is not built, however reasonable it seems.
2. **Done means `scripts/verify.sh full` exits 0** and prints `VERIFY PASSED`. Run it and read
   the result. Never say "should pass". If it cannot pass, say what fails and stop.
3. **Never weaken a gate to get to green.** No skipped or disabled tests, no suppressed
   warnings, no `any`, no lowered thresholds, no edits to protected files
   (`scripts/lib/protected-paths.mjs`). If a gate looks wrong, stop and say why.
4. **Git: your own branch, your own commits.** Work on the task's branch or worktree. Commit
   there when verification passes. Never commit to, merge into or push to `main`; Răzvan
   reviews and merges. Never rewrite pushed history.
5. **The product definition changes only through a Product Change.** Never edit
   `docs/product/model/`. Propose under `docs/product/changes/active/` and stop; Răzvan
   approves and applies. Never re-stamp a stale citation yourself.
6. **Simple and clean.** The plain solution first. Patterns only where
   `docs/engineering/conventions.md` names them. Match the reference slice. No speculative
   abstractions, no dead code, no stray files.
7. **Synthetic data and test credentials only.** Never read `.env` files, never use live
   payment keys, never touch production systems or real personal data (CON-DATA-001).
8. **End every task with a summary**: what changed, each default you chose that is not a
   product rule, new dependencies with their licences, and anything left undone.

## Layout

- `apps/api` — Spring Boot (Java 21, Maven), PostgreSQL, Flyway. Created by task T-001.
- `apps/web` — Next.js (App Router, TypeScript, Tailwind). Created by task T-002.
- `packages/api-types` — TypeScript types generated from the API's OpenAPI document.
- `docs/product/` — the product definition (`model/`), open and applied Product Changes
  (`changes/`), and `open-questions.md`.
- `docs/tasks/` — one file per pull request; `README.md` has the order of work.
- `docs/engineering/` — `quality-gates.md` (what is enforced), `conventions.md` (how we build).
- `scripts/` — `verify.sh` (definition of done), `format.sh`, checks in `lib/`.

## Commands

```sh
scripts/verify.sh fast            # while working
scripts/format.sh                 # before the full run; verify only checks formatting
scripts/verify.sh full            # before committing
pnpm exec prodshape context <ID>… # the cited rules in full, with their neighbours
pnpm exec prodshape inspect <ID>  # one artifact
pnpm exec prodshape impact <ID>   # what depends on an artifact
```

## How a task runs

Use the **ra-task** skill (`/ra-task T-0xx`). In short: read the task, load its rules with
`prodshape context`, check nothing blocks it, implement in the shape of the reference slice,
write tests that name the behaviours (`SB-…`) the task claims, format, verify, ask the
**reviewer** subagent to check the diff against the rules, commit, summarise.

## Product language

Use the product's words in code and UI: a **Coin** (never "product"), a **Listing** (a seller's
coin, Phase 2), a **Reservation**, a **We Buy submission**, **Held funds**, a **Payout**. The
glossary is `docs/product/model/domain/terms/`. English only; prices in euro only.

## Skills and agents

- **ra-task** — carrying out a task from `docs/tasks/` end to end.
- **reviewer** (subagent) — read-only review of a diff against the cited rules and the gates.
- `/product:*` commands and the product skills — reading, auditing and proposing changes to
  the product definition (generated by the ProductShape CLI; do not edit them by hand).

When you learn a durable fact about running or debugging this project, add it to the relevant
skill or to `docs/engineering/` in the same session.
